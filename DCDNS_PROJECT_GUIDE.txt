The guide is written in plain language first and technical detail second. If a
sentence sounds abstract, look for the concrete example next to it.

The central result of the project is stated once here, because every later
section depends on it:

  A replicated registry can tell a client that a write is "committed" before a
  majority of its DNS responders can serve the new state. In the original DCDNS
  write path this happened deterministically: the API acknowledged after a
  majority had STORED an entry, while followers APPLIED it only on a later
  replication push. The primary fix is a write-path publication barrier (B).
  Revision-aware majority DNS (C, RAM-DNS) is a read-side detector that
  complements B; it is not a substitute for B.

B is implemented and validated, but it is currently opt-in through the node flag
--publication-barrier. C is implemented and enabled by default in the demo
resolver. The audit recommends making B the default. This guide does not pretend
that recommendation has already been implemented.


================================================================================
1. THE 60-SECOND EXPLANATION
================================================================================

DCDNS is a working prototype of a permissioned registry for campus DNS names.
A university root authority delegates control of namespaces (for example
cs.test and library.test) to departments. Departments and students then register
names such as techfest.cs.test, prove ownership with Ed25519 signatures, and
manage those names through a web portal.

The registry is not stored on one server. Three registry nodes replicate a
signed, ordered log, and an operation is committed only when a majority (2 of 3)
has stored it. Every registry node is also an authoritative DNS server: it
answers queries from the committed state it holds and attaches its serving
revision to the answer. A client-facing resolver asks all three nodes, returns
an answer only when a majority agrees, and can then check that the agreeing
majority is fresh relative to the committed revision watermark.

That design has a subtle failure. "Committed" and "applied to the DNS snapshot"
are different events. In the original write path, the coordinator acknowledged a
write as soon as a majority had stored it. The two followers had stored the
entry but had not applied it, because they learn the new commit index only on the
next replication push. For a short window, the coordinator served the new answer
while both followers served the old one. The semantic majority was stale, and
the resolver returned the old address even though the registry had committed the
new one. The final baseline run reproduced this in 12 of 12 acknowledged writes;
a larger natural run reproduced it in 20 of 20 trials.

The project evaluates two responses:

  B - Publication barrier (write path, primary fix)
      A write is acknowledged only after a majority reports applying the
      committed revision to the state used for DNS answers. This removes the
      ordinary window. If the majority cannot apply before the deadline, the
      write fails closed with an explicit ambiguous timeout.

  C - RAM-DNS (read path, defence in depth)
      Every DNS answer may carry its serving revision in a signed EDNS(0)
      token. The resolver requires a semantic majority plus a freshness
      condition against a watermark. A stale majority is retried, then refused
      with SERVFAIL (or returned as explicitly marked stale). C detects the
      problem but does not repair the write path.

In one sentence:

  "DCDNS is a permissioned campus DNS registry where authority is delegated,
   state is majority-replicated, every node serves DNS, and the project shows
   why a write acknowledgement must wait for DNS publication - with a read-side
   freshness detector as optional defence in depth."

The short version you can say out loud:

  "It is DNS administration without a central DNS server, plus a careful study
   of the gap between 'the registry committed it' and 'the DNS layer can serve
   it'."


================================================================================
2. WHY WAS THIS PROJECT BUILT?
================================================================================

2.1 The practical problem
-------------------------
A university has one DNS namespace but many departments. Central IT does not
want to manually create every name. Departments want to manage their own names
without asking the centre for every change. At the same time, the university
needs to know:

  - who is allowed to create a name,
  - who owns an existing name,
  - who may change where it points,
  - how a name is revoked when a project ends,
  - how to prove what happened later,
  - what happens when a server crashes,
  - what a client sees immediately after a successful change.

A spreadsheet plus email does not answer those questions. A normal database
does not answer them either, because the hard part is authority, not storage.

2.2 The technical problem
-------------------------
Normal DNS is hierarchical and authoritative. That is good for resolution, but
a campus registry also needs delegated administration, cryptographic ownership,
replication, auditability and revocation. Existing DNS servers can serve a zone
file, but they do not implement the registry rules. Existing databases can store
rows, but they do not speak DNS.

The project asks:

  "Can we build a registry that delegates authority to departments, replicates
   safely across independent nodes, and serves real DNS without a central DNS
   server - and can we state precisely what a successful write promises?"

2.3 The decentralization requirement
------------------------------------
The original goal was not just "decentralize the registry authority". The
requirement was to decentralize DNS itself as much as is honest and practical
for this prototype:

  Level 1: one central registry and one central DNS server.
  Level 2: delegated registry authority, but one DNS publisher/front-end.
  Level 3: every registry node serves DNS from its own committed state, and a
           client-facing resolver requires majority agreement plus revision
           freshness.  <-- THIS PROJECT
  Level 4: peer-to-peer discovery / DHT, with no configured membership.
           Not built. It is a different project with different trade-offs.

DCDNS implements Level 3. There is no separate DNS publisher process. Each node
has its own DNS responder, and the client resolver compares the answers.

2.4 Why this is a useful prototype
----------------------------------
It demonstrates, in one runnable system:

  - delegated namespace authority,
  - Ed25519-signed operations,
  - majority-replicated state,
  - leader takeover and follower catch-up,
  - per-node authoritative DNS,
  - majority agreement over DNS answers,
  - a deterministic acknowledged-write stale-majority failure,
  - a write-path publication barrier that closes the normal-path window,
  - revision-aware freshness that refuses a stale majority,
  - a real web UI,
  - automated security experiments,
  - honest documentation of limitations.

It is meant to be demonstrated, not just described. Every substantive claim in
the UI has a test or an experiment behind it, and the central consistency claim
has a dedicated A/B/C harness.

3. WHAT THE PROJECT ACTUALLY DOES
================================================================================

3.1 User-facing features
------------------------
- Register a name inside a namespace you are allowed to use.
- Update the IPv4 address (A record) of a name you own.
- Transfer ownership to another participant; the recipient must accept.
- Revoke a name; it is withdrawn from DNS and cannot be re-registered.
- Delegate a sub-namespace to another controller.
- Grant a participant permission to register names in a namespace.
- View the operation history of a name.
- View the global audit trail and verify its hash chain.
- View the health of all nodes, their DNS ports, committed and serving revisions.
- See recent DNS queries, each node's vote, and the freshness decision.
- Run security experiments from the browser or the command line.

3.2 System features
-------------------
- Three independent registry processes on ports 9101, 9102 and 9103.
- A signed, ordered operation log on every node.
- Majority commit: a write is committed after 2 of 3 nodes store it.
- Publication barrier B: with --publication-barrier, a write is acknowledged only
  after a majority reports applying it to the DNS state.
- Automatic coordinator (leader) takeover when the current one dies.
- Followers catch up after a restart.
- Each node answers DNS on its own UDP port: 5354, 5355 and 5356.
- A client-facing quorum resolver on UDP 5353.
- The resolver requires 2 of 3 configured nodes to agree.
- Each DNS answer carries a signed EDNS(0) revision token (option 65001).
- The resolver checks RAM-DNS freshness (F1 by default) against the committed
  revision watermark; a stale majority is retried, then refused.
- If no majority agrees, the resolver returns SERVFAIL.
- A metrics endpoint on http://127.0.0.1:5380/metrics.
- A portal on http://127.0.0.1:8000.
- A one-command launcher with a supervisor that restarts crashed children.
- Loopback-only chaos controls for lying-node, pause, freeze and commit-hold
  experiments.

3.3 What a normal demo looks like
---------------------------------
1. Start the system with: python run_demo.py --fresh
2. Open http://127.0.0.1:8000.
3. The dashboard shows three nodes, one coordinator, all at the same revision.
4. It also shows three per-node DNS authorities and a quorum resolver.
5. Register myproject.cs.test as Alice.
6. Query it with: python -m dcdns.dig myproject.cs.test --all
7. All three nodes and the quorum resolver return 10.20.5.50.
8. Change the address; after the commit is applied, the new answer appears.
9. Switch to Mallory and try to change Alice's name; the registry rejects it.
10. Run the lying-node experiment; n3 returns a forgery, the resolver returns
    the honest majority answer.
11. Revoke the name; it disappears from DNS everywhere.
12. Stop one node; the other two still answer and still form a DNS majority.
13. Stop two nodes; writes are refused and DNS returns SERVFAIL.

The normal demo uses the baseline write path, because the launcher does not yet
expose the barrier. The stale-majority window is therefore still demonstrable;
the audit harness is the controlled way to compare baseline and barrier.


================================================================================
4. WHAT THIS PROJECT IS NOT
================================================================================

Be precise about this. It prevents embarrassing questions later.

- It is NOT a blockchain.
  There are no blocks, no mining, no tokens, no proof-of-work and no public
  consensus. It is a permissioned registry with a replicated log.

- It is NOT a trustless system.
  A root authority bootstraps trust. The set of nodes is configured. The demo
  portal holds private keys. These are deliberate prototype choices.

- It is NOT a peer-to-peer or DHT discovery system.
  Nodes know each other from configuration. There is no gossip-based membership
  discovery. Level 4 was explicitly left out.

- It is NOT Byzantine-fault-tolerant consensus.
  The registry protocol tolerates crashes and omissions, not a node that
  maliciously violates the replication protocol. The DNS layer can outvote one
  lying node, but that is a read-time majority check, not BFT consensus.

- It is NOT a production PKI.
  Key enrolment, recovery, hardware-backed signing and certificate chains are
  documented as future work, not implemented.

- It is NOT a full DNS implementation.
  It supports IPv4 A records in the .test zone. There is no AAAA, TXT, CNAME,
  MX, zone transfer, recursion, DNSSEC or public internet delegation.

- It is NOT a general-purpose registrar.
  The record policy only permits private/campus IPv4 addresses. That is a
  feature for a campus registry, not a bug.

- It is NOT a replacement for the university's existing DNS.
  It is a lab prototype for .test. A real deployment would integrate with the
  university's owned zone and existing DNS/DHCP infrastructure.

- It is NOT highly available across data centres.
  All three nodes run on one machine in the demo. Real network partitions are
  approximated by process death and synthetic holds. Throughput and WAN latency
  are not measured.

- It is NOT a claim that RAM-DNS is novel.
  The academic review concludes that the stale-DNS phenomenon is real and
  impactful, while the novelty and incremental benefit of RAM-DNS are not
  established. A professional prior-art search is still required.


================================================================================
5. CORE CONCEPTS IN SIMPLE TERMS
================================================================================

5.1 Registry
------------
The authoritative record of namespaces, domains, owners, records and history.
In DCDNS it is a deterministic state machine fed by signed operations.

5.2 DNS
-------
The Domain Name System: a distributed naming system that maps names such as
techfest.cs.test to data such as IPv4 addresses.

5.3 Zone
--------
The portion of the DNS namespace for which a server is authoritative. Here the
lab zone is .test, and each node builds a flat name -> address snapshot from its
committed registry state.

5.4 Authoritative DNS server
----------------------------
A server that gives the definitive answer for a zone, rather than forwarding to
another resolver. Every DCDNS registry node runs one.

5.5 Recursive resolver / forwarder
----------------------------------
A resolver that accepts a client query and obtains the answer from other servers.
DCDNS's quorum resolver is a forwarder: it queries the three authoritative nodes
and applies a decision rule. It is not a general recursive resolver.

5.6 Namespace
-------------
A subtree of names, such as cs.test or team.cs.test, controlled by a participant.

5.7 Domain name
---------------
A fully qualified name such as techfest.cs.test.

5.8 Record
----------
The data attached to a name. DCDNS supports an IPv4 A record per domain.

5.9 TTL
-------
Time to live: how long a cache may reuse an answer. DCDNS uses a 30-second TTL
for normal answers. TTL is a cache-lifetime control, not a freshness proof.

5.10 Delegation
---------------
Granting control of a sub-namespace to another controller. Delegation is
top-down and recorded in the signed log.

5.11 Controller
---------------
The participant authorized to administer a namespace: delegate children, grant
members, register names, and revoke within that subtree.

5.12 Owner
----------
The participant that controls a specific domain's records.

5.13 Member
-----------
A participant granted a narrow permission, such as can_register, inside a
namespace.

5.14 Operation
--------------
A signed request such as register_domain or update_records.

5.15 Signature
--------------
An Ed25519 signature over canonical JSON with a domain-separation prefix. It
proves which key authorized an operation.

5.16 Key pair
-------------
A private signing key and its public verification key. In DCDNS the public key
is the identity.

5.17 Fingerprint
----------------
A short hash of a public key, used for display and comparison.

5.18 Nonce
----------
A random value included in a signed operation and recorded by the state machine.
It makes byte-for-byte replay detectable.

5.19 Revision
-------------
A monotonically increasing counter of applied committed operations. It is the
registry's version number and the value used in DNS freshness evidence.

5.20 Log and log index
----------------------
The ordered list of operations. The index is the position in that list. Commit
index is the highest index known to be committed.

5.21 Quorum
-----------
A majority: floor(N/2) + 1. For three nodes, two.

5.22 Coordinator (called "leader" in the code)
----------------------------------------------
The node allowed to append new entries for the current term. It is elected by a
deterministic rule from the reachable majority, not appointed as a central
authority.

5.23 Follower / replica
-----------------------
A node that stores and applies entries sent by the coordinator. Followers never
originate entries.

5.24 Commit
-----------
The point at which a majority has durably stored an entry. Commit is necessary
for durability but does not by itself mean the entry has been applied or that
DNS can serve it.

5.25 Apply
----------
Executing a committed entry in the deterministic state machine and refreshing the
DNS snapshot. This is the step that makes the new state visible to DNS.

5.26 Publication barrier
------------------------
The rule that a write is acknowledged only after a majority reports applying the
committed revision. It turns "committed" into a stronger publication promise.

5.27 Watermark
--------------
The best-known committed revision used by the read-side freshness check. In the
default responses mode it is the highest serving revision observed in the DNS
responses.

5.28 Stale majority
-------------------
A semantic majority that agrees on an old committed answer while a newer
committed revision is visible elsewhere.

5.29 Audit chain
----------------
A hash-chained list of accepted operations. Editing one record breaks every
later hash.

5.30 NOERROR, NXDOMAIN, SERVFAIL
--------------------------------
NOERROR means the name exists and an answer is present (or the query succeeded
with no data). NXDOMAIN means the name does not exist. SERVFAIL means the
resolver could not produce a trustworthy answer.

5.31 .test
----------
A reserved testing TLD (RFC 6761). It will not collide with a real public name.

6. SYSTEM ARCHITECTURE
================================================================================

6.1 The two planes
------------------
Registry plane:
  signed operations -> deterministic state machine -> replicated log ->
  committed state -> audit history and DNS snapshot.

DNS plane:
  committed snapshot -> per-node authoritative responder -> client quorum
  resolver -> DNS client.

The planes are coupled by the snapshot refresh, but their quorums are separate.
A registry write can commit while DNS lacks a quorum, and DNS can answer while a
write is still being ordered.

6.2 Diagram
-----------
                        Portal (FastAPI + Jinja2)
                                   |
                                   | signed operations (Ed25519)
                                   v
                 +-----------------+-----------------+
                 |                 |                 |
            Registry n1       Registry n2       Registry n3
            API 9101          API 9102          API 9103
            DNS 5354          DNS 5355          DNS 5356
                 |                 |                 |
                 +-------- quorum-replicated log -----+
                                   |
                        committed registry state
                                   |
                 +-----------------+-----------------+
                 |                 |                 |
            DNS responder     DNS responder     DNS responder
                 |                 |                 |
                 +------- client quorum resolver ----+
                              UDP 5353
                                   |
                          dig / DNS client
                    (answer only if 2 of 3 agree)

6.3 Components and ports
------------------------
Portal               http://127.0.0.1:8000
Node HTTP APIs       127.0.0.1:9101, 9102, 9103
Node DNS responders  UDP 5354, 5355, 5356
Quorum resolver      UDP 5353
Resolver metrics     http://127.0.0.1:5380/metrics
Node data            data/live/n1, n2, n3
Node logs            data/live/logs/n1.log, n2.log, n3.log

6.4 Why three nodes?
--------------------
Three is the smallest useful majority. One node down: 2 of 3 still commit and
still answer DNS. Two down: no majority, so writes stop and DNS returns SERVFAIL.
One liar: the other two outvote it. Two liars: they can outvote the honest node,
which is the documented boundary.

6.5 What talks to what
----------------------
- The portal signs operations and sends them to the cluster client.
- The client may send to any node; a follower forwards to the coordinator.
- The coordinator replicates to followers over HTTP.
- Each node's DNS responder reads its own committed snapshot.
- The resolver queries all node responders over UDP.
- The portal reads node status and resolver metrics over HTTP.

6.6 Trust boundaries at a glance
--------------------------------
  untrusted                     trust boundary                  trusted
  ---------                     --------------                  -------
  any client  --signed op-->  [ verify signature ]  -->  state machine
  any client  --signed op-->  [ namespace policy ]  -->  state machine
  follower    --append RPC->  [ term / log rules ]  -->  replicated log
  DNS client  --query------>  [ 2-of-3 agreement + freshness ]  -->  answer or SERVFAIL

The registry never trusts the transport. A node that receives an operation
verifies it itself; it does not rely on the forwarding node having done so.

================================================================================
8. IDENTITIES AND CRYPTOGRAPHY
================================================================================

8.1 Identity is a public key
----------------------------
A participant is identified by an Ed25519 public key. The demo gives friendly
labels (alice, bob, root) to those keys, but the label is not the identity.

8.2 What is signed
------------------
The signed bytes are:

  "DCDNS-OP-V1\n" + canonical_json(envelope without sig)

The envelope includes version, actor, nonce, timestamp, operation and body. The
domain-separation prefix prevents these signatures from being confused with DNS
revision-token signatures.

8.3 Why canonical JSON matters
------------------------------
JSON object order is not semantically meaningful, but signature bytes are.
Canonical serialization makes verification deterministic across nodes and
languages.

8.4 Nonce and replay
--------------------
The state machine records actor|nonce for accepted operations. A byte-for-byte
resubmission is rejected with REPLAY_DETECTED even though the signature is still
valid. A genuinely new operation needs a new nonce.

8.5 Timestamp
-------------
A coarse clock sanity check rejects operations more than 900 seconds away from
the node's clock. It is not a full trusted-time protocol.

8.6 The demo identities
-----------------------
root            root authority
cs-admin        controller of cs.test
library-admin   controller of library.test
alice           member with can_register in cs.test
bob             controller of team.cs.test
mallory         unaffiliated attacker

8.7 Where keys are stored
-------------------------
identities/*.json for the demo participants; data/live/node-keys/ for node DNS
signing keys. This is convenient and insecure by production standards. The
portal holds private keys and signs on the selected identity's behalf.

8.8 What the root can and cannot do
-----------------------------------
The root can delegate namespaces, register names and revoke. It cannot forge an
owner's signature. Any root action is a root-signed operation in the audit log.
The root trust anchor is a documented centralization point.


================================================================================
9. NAMESPACES AND AUTHORITY
================================================================================

9.1 The namespace tree
----------------------
The root owns the top of the lab namespace. It delegates cs.test and
library.test to departmental controllers. A controller may delegate a child such
as team.cs.test to another participant and grant narrow member permissions.

9.2 Who may do what
-------------------
- Root: delegate top-level namespaces, register anywhere, revoke.
- Namespace controller: delegate children, grant members, register inside the
  namespace, revoke inside it.
- Member with can_register: register inside the granted namespace.
- Owner: update records, initiate transfer, cancel transfer, revoke the domain.
- Recipient: accept a pending transfer.

9.3 Delegation is top-down
--------------------------
A child namespace must be created by its parent's controller. There is no
sideways takeover.

9.4 Revocation is terminal
--------------------------
A revoked domain remains as a tombstone. It leaves DNS, cannot be updated, and
cannot be re-registered. The same applies to a revoked namespace.

9.5 What is decentralized here?
-------------------------------
Authority is delegated; state is replicated; every node serves DNS; the client
answer is decided by majority agreement plus freshness. What is not
decentralized: the root trust anchor, configured membership, and demo key
custody.


================================================================================
10. DOMAIN LIFECYCLE AND RECORD POLICY
================================================================================

10.1 Lifecycle
--------------
  absent -> active -> pending_transfer -> active (new owner)
  active -> revoked
  pending_transfer -> active (old owner, after cancel)

A domain is created by register_domain inside a namespace where the signer has
authority. It becomes active immediately. A transfer freezes the record until
the recipient accepts or the transfer is cancelled. Revocation is terminal.

10.2 Why records freeze during transfer
---------------------------------------
Freezing prevents the old owner from changing the address mid-handover and
prevents the recipient from taking control before accepting. The frozen record
keeps resolving, so a handover does not cause downtime.

10.3 DNS publication rule
-------------------------
A node's DNS snapshot includes active domains in active namespaces, plus domains
in a pending transfer using their frozen record. Revoked domains and revoked
namespaces are excluded. The snapshot is rebuilt after committed state changes.

10.4 Record policy
------------------
Only IPv4 A records are supported. Addresses must be in the permitted campus
space; arbitrary public destinations are rejected with RECORD_NOT_ALLOWED. This
is a campus policy, not a general DNS policy.

10.5 Name syntax
----------------
Lower-case labels, dot-separated, length limits enforced. Names must end in
.test in the demo. Invalid names are rejected before they reach the log.

10.6 Revocation and DNS timing
------------------------------
After a revocation commits and the node applies it, the name disappears from the
snapshot and queries return NXDOMAIN. A cache may still serve the old answer
until its TTL expires; that is inherent to DNS and is measured separately.

10.7 No re-registration
-----------------------
The tombstone prevents a revoked project name from being quietly taken over.

11. OPERATIONS AND VALIDATION
================================================================================

11.1 The ten operations
-----------------------
1.  delegate_namespace
2.  grant_member
3.  register_domain
4.  update_records
5.  transfer_initiate
6.  transfer_accept
7.  transfer_cancel
8.  revoke_domain
9.  revoke_namespace
10. rotate_controller

11.2 Validation order
---------------------
1. Envelope shape and version.
2. Actor public key and signature.
3. Timestamp window.
4. Nonce replay check.
5. Namespace/domain existence.
6. Authorization by longest enclosing namespace.
7. Record policy.
8. State transition legality (for example, transfer pending).

The coordinator runs the full check on a clone before appending. Invalid
operations never consume a log slot.

11.3 Main error codes
---------------------
NAME_TAKEN, NOT_FOUND, UNAUTHORIZED, INVALID_SIGNATURE, REPLAY_DETECTED,
STALE_OPERATION, RECORD_NOT_ALLOWED, INVALID_NAME, TRANSFER_PENDING,
NO_PENDING_TRANSFER, REVOKED, NO_QUORUM, NOT_LEADER.

11.4 HTTP status codes
----------------------
400  malformed input, invalid name, invalid record, replay, stale timestamp
401  invalid signature
403  unauthorized
404  name/namespace not found
409  conflict: taken, revoked, transfer pending, no pending transfer
503  no quorum

The exact error code matters more than the HTTP status for the experiments. The
tests assert the code, not just "it failed".


================================================================================
12. HOW A WRITE WORKS, STEP BY STEP
================================================================================

This is the most important flow to understand. Follow one update.

Step 1: The client builds an operation
--------------------------------------
The portal (or a script) creates an unsigned envelope:

  op = update_records
  actor = Alice's public key
  body = { "name": "techfest.cs.test", "records": { "A": "10.20.5.99" } }
  nonce = random 32 hex chars
  ts = current Unix time

Step 2: The client signs it
---------------------------
The private key signs the domain-separated canonical JSON. The operation is now
self-contained: anyone with Alice's public key can verify it without contacting
Alice.

Step 3: The client sends it to any node
---------------------------------------
The portal uses the cluster client, which tries the configured node URLs. A
script can POST directly to 9101, 9102 or 9103. It does not matter which node
receives it.

Step 4: The receiving node checks the timestamp
-----------------------------------------------
If the timestamp is more than 900 seconds away from the node's clock, the node
returns STALE_OPERATION.

Step 5: A follower forwards to the coordinator
----------------------------------------------
If the receiving node is not the coordinator, it returns NOT_LEADER with the
coordinator's URL. The HTTP layer forwards the operation once, marked with
X-DCDNS-Forwarded.

Step 6: The coordinator validates on a clone
--------------------------------------------
The coordinator calls state.probe(op), which applies the operation to a deep copy
of the state. The full authorization and record policy runs. If it fails, the
error is returned and nothing is appended. An invalid operation never wastes a
log slot or forces followers to store garbage.

Step 7: The coordinator appends and persists
--------------------------------------------
The operation gets the next log index i. The entry is appended to the in-memory
log and written to data/live/<node>/log.jsonl. The coordinator does not yet tell
the client "committed".

Step 8: The coordinator replicates
----------------------------------
The coordinator sends the entry to the other nodes via POST /internal/append.
Followers store it and report their last index. The coordinator tracks how many
nodes have stored each index.

Important detail: _replicate() snapshots the commit index BEFORE it pushes. The
first push for entry i therefore advertises commit_index = i - 1.

Step 9: Majority commit
-----------------------
When at least 2 of 3 nodes (including the coordinator) have stored the entry, the
commit index advances to i. The state machine applies the operation for real.
The revision increments, history and audit records are appended, and the nonce is
recorded.

Step 10: The DNS snapshot refreshes
-----------------------------------
Applying committed state triggers _refresh_dns_zone(). The node rebuilds a flat
name -> IPv4 map from snapshot_for_dns() and swaps it in atomically. The DNS
responder thread reads that map without locks. The node's dns_revision becomes
the applied revision.

Step 11a: Baseline acknowledgement
----------------------------------
In the original path, submit() returns success as soon as commit_index >= i.
At that moment the coordinator has applied entry i, but the followers have only
stored it. They will apply it when the next heartbeat pushes commit_index = i.
The client is told "committed" while a majority still serves revision i - 1.

Step 11b: Barrier acknowledgement (variant B)
---------------------------------------------
With --publication-barrier, submit() additionally requires:

  _applied_majority(i) == True

That function counts the coordinator only after its own dns_revision >= i, and
counts a live follower only when the append response reports dns_revision >= i.
If the first round committed the entry but the followers have not applied it,
the coordinator pushes again with commit_index = i and re-checks. Only then does
it return success.

The promise becomes:

  "The operation is committed and a majority of registry nodes have applied the
   committed revision to the state from which they serve DNS."

What if the write times out?
----------------------------
If the entry is appended but does not reach a majority before the write timeout,
the node raises NO_QUORUM with an "ambiguous write" message. The operation may
still commit later. The API reports ambiguous: true rather than pretending it
definitely failed.

With B, a timeout can also happen after commit but before the applied majority
is reached. That is still ambiguous: the write may become visible later. A
non-idempotent operation such as a transfer or revocation must therefore not be
blindly retried without de-duplication. Idempotency keys are a documented next
step, not an implemented guarantee.

What if the client retries?
---------------------------
The nonce is the same if the client resends the exact same signed operation. If
it committed, the retry gets REPLAY_DETECTED. A well-behaved client should query
the state or use a new nonce for a genuinely new operation.

Why the clone/probe step matters
--------------------------------
Without it, a malicious or malformed operation would be written to the log, then
every follower would have to apply it and reject it. The log would fill with
garbage and revisions could diverge. Probing first keeps the log clean and makes
rejection deterministic and cheap.


================================================================================
13. REPLICATION AND CONSENSUS
================================================================================

13.1 What the cluster guarantees
--------------------------------
- Total order: all committed operations have one order.
- Majority durability: a committed write survives the loss of any one node.
- Convergence: a restarted or lagging follower catches up to the committed log.
- Continued writes while one of three nodes is down.
- Write refusal when a majority is unavailable.
- With B: a successful write has been applied by a majority, not merely stored.

13.2 The protocol in plain language
-----------------------------------
- The nodes form a full mesh: each node knows the other two.
- The coordinator is the lowest-id node among the reachable majority.
- Only the coordinator appends new entries.
- Followers never originate entries; they only store and apply what the
  coordinator sends.
- Because there is one writer, every node's log is a prefix of the coordinator's
  log. Catch-up is append-only; there is no need to truncate conflicting entries.
- A write is committed when a majority has stored it.
- With B, it is acknowledged when a majority has applied it.
- If the coordinator dies, the lowest-id node in the new reachable majority takes
  over.
- A new coordinator pulls any longer log from peers before writing.

This is not Raft. There is no vote request/vote response protocol and no log
truncation. The design is simpler because the workload allows a single writer and
followers never create entries.

13.3 Terms and roles
--------------------
- term: a leadership epoch. It increments when a node assumes leadership.
- leader_id: the node currently believed to be coordinator.
- role(): "leader", "follower" or "isolated".
- isolated: the node cannot see a majority; it refuses writes.

A follower that receives an append with a higher term updates its term. A stale
coordinator's append is rejected by a follower with a higher term.

13.4 How commit advances
------------------------
For each index, the coordinator counts how many live nodes have stored at least
that index. If the count is at least quorum (2 of 3), the commit index advances.
The coordinator persists meta.json and applies the newly committed entries.

13.5 How catch-up works
-----------------------
- The coordinator tracks peer_last: the last index each peer confirmed.
- It sends entries from peer_last + 1, up to 64 at a time.
- A restarted follower loads its log and meta, replays the committed prefix, and
  then receives the missing tail.
- A new coordinator calls _adopt_longest_log(): it asks peers for their last
  index and pulls any missing entries before it starts writing.

13.6 Failure scenarios
----------------------
One follower down:
  - The coordinator and the other follower still form a majority.
  - Writes commit (2 of 3).
  - DNS: the two live nodes answer; the quorum resolver gets 2 agreeing answers.

The coordinator down:
  - The remaining two nodes see a majority and elect the lowest-id of the two.
  - A new term starts.
  - Writes commit.
  - DNS: the two live nodes answer; the resolver still gets 2 agreeing answers.

The old coordinator restarts:
  - It loads its log, catches up, and may become coordinator again because it has
    the lowest id. This is expected, not a bug.

Two nodes down:
  - The remaining node is isolated (1 of 3 is not a majority).
  - Writes are refused with NO_QUORUM.
  - DNS: the single node may answer directly, but the quorum resolver requires 2
    of 3 configured nodes, so it returns SERVFAIL.

A node with a stale state:
  - It answers DNS from what it has committed, and publishes that serving
    revision in the EDNS token.
  - If it is the only stale node, the other two outvote it.
  - If two nodes are stale, the semantic majority is stale. RAM-DNS compares the
    majority's revisions with the watermark and fails closed instead of serving
    the old answer. This is the stale-majority experiment.
  - With B, the ordinary commit/apply window is closed before the write is
    acknowledged. B does not cover a responder that is deliberately frozen at an
    older snapshot.

13.7 Why is there a leader? Is that not centralization?
-------------------------------------------------------
This is the most common question. The answer has two parts.

First, the leader is a role, not a central server:
  - It is elected from the nodes by a deterministic rule.
  - It has no extra signing key and no authority over content.
  - It cannot change a record without a valid owner/controller signature.
  - It can be killed; another node takes over.
  - Every node can receive a client write and forward it.
  - The cluster is a full mesh; the leader is not a hub in the topology.

Second, a single writer is needed for a registry:
  - Unique names require one order of operations.
  - Ownership transfer and replay nonces require a single serialization point.
  - If two nodes could accept conflicting writes, two people could both believe
    they own the same name.
  - A leaderless multi-writer design would need Byzantine consensus (which still
    has a proposer/leader per view) or conflict-free data types (which cannot
    enforce exclusive ownership cleanly).

So the honest sentence is:

  "The leader is a temporary write coordinator elected by a majority. It is not
   a central authority; authority comes from signatures and delegated
   namespaces."

13.8 Known limitations of the replication layer
-----------------------------------------------
- Not Byzantine-fault tolerant. A malicious node could violate the protocol.
- No vote protocol. The deterministic lowest-id rule assumes nodes converge on a
  similar live set. Arbitrary asymmetric network partitions are not formally
  solved; the demo tests process death and synthetic holds, not real link failure.
- Static membership. The peer set comes from configuration; there is no dynamic
  add/remove.
- No log compaction. The log grows without bound.
- No snapshots. State is rebuilt by replay.
- Ambiguous writes on timeout. The client may not know whether a write committed.
- Reads from followers may lag. consistent=true forces a coordinator read.
- B trusts self-reported peer dns_revision. A lying follower could claim a
  revision it does not have. B is not Byzantine-safe.

13.9 Evidence that replication works
------------------------------------
scripts/cluster_smoke.py starts three real processes and runs nine checks:

  1. registration committed by a majority,
  2. all three nodes converge to the same revision,
  3. a forged update is rejected,
  4. a write commits with one follower stopped (2 of 3),
  5. the stopped follower rejoins and catches up,
  6. the leader is killed and a new leader takes over,
  7. a write commits after failover,
  8. the old leader restarts and catches up,
  9. writes are refused when two nodes are down.

Latest result: 9/9 cluster checks passed.


================================================================================
14. DNS: THE DECENTRALIZED PART
================================================================================

This is the heart of the project and the part most likely to be questioned.

14.1 The old design versus the new design
-----------------------------------------
Old design (Level 2):
  registry nodes -> one publisher polls committed state -> one DNS front-end
  -> clients.

That decentralizes registry authority but leaves DNS trust in one process. If
that process lies or dies, clients are affected.

New design (Level 3):
  every registry node has its own DNS responder,
  and a client-facing resolver asks all nodes and requires a majority.

There is no DNS publisher. There is no single DNS server that owns the zone.

14.2 Per-node DNS responder
---------------------------
Each node runs a NodeDNSResponder thread:

  - binds UDP on its own port (5354, 5355 or 5356),
  - reads the node's committed dns_zone snapshot,
  - answers A and ANY queries,
  - returns NXDOMAIN for unknown names,
  - returns NOTIMP for unsupported types,
  - sets the AA (authoritative answer) bit,
  - uses a 30-second TTL,
  - attaches a signed EDNS(0) revision token when configured,
  - records query metrics.

The responder does not read the registry database directly. It reads the flat
snapshot that was built from committed state. A follower may be behind the
coordinator; that is visible in its revision.

14.3 The client-facing quorum resolver
--------------------------------------
The QuorumResolver process on UDP 5353:

  - receives a DNS query from a client,
  - forwards the same query to all three node responders,
  - waits up to 0.75 seconds per node (configurable),
  - reduces each response to its semantic content,
  - groups identical answers,
  - returns an answer only if at least 2 of 3 nodes agree,
  - otherwise returns SERVFAIL with the original question.

It is a majority-vote forwarder, not an authority. It has no zone of its own and
no private keys. It cannot create a record. It only compares what the nodes say.

14.4 What "semantic agreement" means
------------------------------------
The resolver does not compare raw packets. It compares what a client would act
on:

  - the RCODE (NOERROR, NXDOMAIN, etc.),
  - the answer records: type, class and RDATA,
  - with records sorted so order does not matter.

It deliberately ignores:

  - the transaction ID (the resolver patches the client's ID back in),
  - harmless flags,
  - TTL differences,
  - record order.

So two nodes agree if they return the same address for the same name, even if
their packets differ in cosmetic ways.

14.5 Decision table
-------------------
Situation                          Resolver behaviour
---------------------------------- --------------------------------------------
All 3 nodes return the same answer  Return it (3 votes).
2 nodes agree, 1 is down            Return the majority answer (2 votes).
2 nodes agree, 1 returns a forgery  Return the majority answer; count a
                                    disagreement; the liar is outvoted.
2 nodes agree on NXDOMAIN           Return NXDOMAIN.
1 node answers, 2 are down          SERVFAIL. One node cannot speak for the
                                    cluster.
3 nodes return 3 different answers  SERVFAIL. No majority.
2 nodes return different answers    SERVFAIL. No majority.
A node returns a malformed packet   It does not count as a vote; if the other
                                    two agree, return their answer.
Two nodes collude on a forgery      The resolver accepts it. This is the
                                    documented majority trust boundary.

14.6 Why not just query one node?
---------------------------------
Because one node can be:

  - down,
  - stale,
  - compromised,
  - configured with a different state.

A single node is a single point of trust. Requiring two independent nodes to
agree removes that single point for one-fault scenarios. It is the DNS analogue
of quorum commit.

14.7 Why 2 of 3 and not 3 of 3?
-------------------------------
2 of 3 tolerates one failure or one liar while still making progress. 3 of 3
would stop on any single fault, which defeats the resilience goal. 1 of 3 would
let one node decide, which defeats the trust goal. 2 of 3 is the smallest useful
majority.

14.8 Is the quorum resolver a single point of failure?
------------------------------------------------------
It is a single process in the demo, but it is not a single point of authority:

  - It has no zone and no keys; it cannot invent an answer.
  - A client can query any node directly.
  - You can run multiple resolvers; they will all compare the same nodes.
  - If the resolver dies, clients pointed at it fail, but no registry data is
    lost and the authoritative nodes keep serving.

In a production design, the resolver function would be replicated or built into
clients/stub resolvers. The important property is that the decision rule is
majority agreement, not the identity of one process.

14.9 What is still centralized?
-------------------------------
Be honest about this:

  - The set of nodes is configured. There is no P2P/DHT discovery.
  - The root trust anchor is centralized by design.
  - The .test zone is a lab; it is not delegated from the real DNS root.
  - The demo portal holds private keys.
  - The quorum threshold is a configuration choice.
  - DNSSEC is not implemented; the EDNS revision token is an application-layer
    attestation, not a DNSSEC signature.

What is decentralized:

  - registry state is replicated across independent nodes,
  - namespace administration is delegated,
  - every node serves DNS,
  - the client answer is decided by majority agreement plus revision freshness,
    not by one server.

14.10 How to query it
---------------------
On Windows, nslookup does not support a custom port. Use the project's client:

  python -m dcdns.dig techfest.cs.test
  python -m dcdns.dig techfest.cs.test --all
  python -m dcdns.dig techfest.cs.test --port 5354

On Linux/macOS with dig:

  dig @127.0.0.1 -p 5353 techfest.cs.test A
  dig @127.0.0.1 -p 5354 techfest.cs.test A

The --all output shows the quorum answer and each node's answer side by side.
That is the clearest way to demonstrate the majority rule.

14.11 Metrics and what they mean
--------------------------------
http://127.0.0.1:5380/metrics returns JSON:

  published_revision   The lowest committed revision among reachable nodes. This
                       is a conservative "everyone has at least this" number.
  serving_revision     The lowest serving revision among reachable nodes.
  zone_size            The largest zone reported by a reachable node.
  source               "majority of 2 of 3 nodes".
  queries              Queries received by the resolver.
  answered             Queries that got a majority answer.
  nxdomain             Majority answers that were NXDOMAIN.
  servfail             Queries that returned SERVFAIL, including stale-majority
                       failures.
  disagreements        Queries where the nodes did not all agree (even if a
                       majority still answered).
  quorum               Required votes (2).
  watermark            Committed revision watermark of the last decision.
  freshness            Policy (condition, delta, watermark source, stale policy,
                       retry budget) and counters: stale_majority_queries,
                       freshness_failures, stale_answers, retries,
                       missing_revision, invalid_revision, last_reason.
  nodes                Per-node reachability, committed revision, serving
                       revision, lag, frozen state, zone size, overrides.
  recent               Last queries with per-node votes, revision evidence,
                       watermark, freshness reason and retries.

A disagreement is not necessarily a failure. It means the nodes did not speak
with one voice; the majority answer may still be correct. A SERVFAIL means no
majority was reached, or the majority was stale and the policy failed closed.

14.12 The lying-node demo
-------------------------
The demo enables a loopback-only chaos endpoint on each node. It can override one
name's answer in memory:

  POST http://127.0.0.1:9103/internal/chaos
  { "name": "techfest.cs.test", "address": "10.20.5.66" }

Now n3 lies. The quorum resolver still returns the honest answer from n1 and n2.
Directly querying n3 returns the forgery. Clear it with:

  POST http://127.0.0.1:9103/internal/chaos
  { "clear": true }

The portal experiment "Majority DNS resists a lying node" does this automatically
and clears the override in a finally block. The override is in-memory only;
restarting the node clears it. Chaos is disabled unless the node is started with
--chaos, and the endpoint is loopback-only. It is a demo feature, not a
production feature.

14.13 What DNSSEC would add
---------------------------
The registry signatures secure operations, not DNS answers. A client querying a
node directly does not verify a cryptographic signature on the DNS response. The
quorum resolver provides majority agreement, not cryptographic proof.

DNSSEC would sign the zone data so a resolver could verify the answer
cryptographically. It is not implemented. In a production system, signed zone
snapshots or DNSSEC would reduce reliance on majority trust. This is a clear
future-work item and a good answer to "how do you know a node did not lie?":
"One node is outvoted by majority; for cryptographic proof we would add DNSSEC."

14.14 What is RAM-DNS?
----------------------
RAM-DNS means revision-aware majority DNS. It is the read-side freshness rule
added on top of the semantic majority. It is variant C in the audit. It is not
the primary write-path fix.

The problem:

  - n1 and n2 are at revision 10 and answer 10.20.5.42.
  - n3 is at revision 11 and answers 10.20.5.99.
  - n1 and n2 are a semantic majority, so the old answer wins.
  - They are not lying; they are serving a real older committed snapshot.

The mechanism:

  - Each node attaches its serving revision, a zone digest and an optional
    Ed25519 signature to the DNS answer in EDNS option 65001.
  - The resolver computes a watermark from the responses (by default the highest
    revision observed).
  - It then applies a freshness condition to the winning majority:
      F1: at least one majority node is at the watermark (default),
      F2: a quorum of the majority is within a bounded lag,
      F3: every majority node is within a bounded lag.
  - A stale majority is retried a bounded number of times. If it stays stale,
    the resolver returns SERVFAIL (default) or an explicitly marked stale answer
    with EDNS option 65002 and a reduced TTL.

What it does not do:

  - It is not BFT. Two colluding nodes can still form a false majority.
  - It does not replace DNSSEC. The token is an application-layer attestation,
    not a DNSSEC signature.
  - A single node claiming a fake high revision can force fail-closed behaviour
    under the responses watermark; signed tokens identify the claimant but do
    not make the claim true.
  - If no responder has seen a newer commit, a response-based watermark cannot
    know about it.
  - It does not fix the write path. On the baseline cluster it converts the stale
    window into SERVFAIL, which is safer but less available.

The live stale-majority experiment freezes n1 and n2 at a real committed
snapshot, commits a new address, waits for n3 to serve it, and compares the
semantic-only resolver with RAM-DNS. The semantic-only resolver returns the old
address; RAM-DNS returns SERVFAIL at the newer watermark. After thaw, the new
answer is served. See docs/RAM_DNS.md for the wire format and results.

14.15 The publication barrier and RAM-DNS together
--------------------------------------------------
B and C are complementary:

  - B fixes the ordinary commit/apply window on the write path.
  - C detects staleness on the read path, including a frozen responder, when a
    newer revision is visible.
  - B's current check uses the registry's dns_revision, not the responder's
    serving_revision. A deliberately frozen responder can therefore still let B
    acknowledge. C remains useful in front of such a deployment.
  - Neither mechanism is Byzantine-safe. B trusts self-reported peer revisions;
    C's signature proves authorship, not truth.

The audit's recommendation is B as the default write-path behaviour, with C as
optional defence in depth. That is a recommendation, not the current default.


================================================================================
15. SECURITY MODEL AND THREAT MODEL
================================================================================

15.1 Assets
-----------
- Namespace delegation records: whoever controls a namespace controls every name
  inside it.
- Domain ownership records: determines who may change where a name points.
- Record contents (A): redirects traffic for a campus name.
- Audit log: evidence of who changed what and when.
- Private keys: possession is identity.
- DNS answers: what users and applications act on.

15.2 Adversaries considered
---------------------------
- Unaffiliated network user: can call the API, submit signed operations, read
  public state.
- Malicious student: has a valid key but no authority over the target namespace.
- Compromised department key: can act fully inside that department's subtree.
- Network attacker: can drop, delay or reorder packets.
- Node operator (honest-but-curious): can read local state and logs.
- Crashed node: stops responding; may restart with stale state.
- Lying DNS node: returns a wrong answer while still participating (handled at
  the DNS read layer by majority agreement, not by registry consensus).

Out of scope for the registry consensus: a node that actively lies while
participating in consensus (Byzantine), a compromised root key, and physical
access to the host.

15.3 Threats and mitigations
----------------------------
Impersonation
  Attack: submit an operation claiming to be someone else.
  Mitigation: the actor is inside the signed bytes; changing it breaks the
  signature. Every node verifies, not just the entry point.
  Residual: private-key compromise.

Tampering in flight
  Attack: change the record value after signing.
  Mitigation: canonical serialization over the full envelope; any change breaks
  verification. There is no unsigned field that affects state.
  Test: invalid signature experiment.

Replay
  Attack: resubmit a previously accepted operation.
  Mitigation: nonce recorded per actor; replay rejected deterministically.
  Residual: the nonce table grows with operation count.
  Test: replay experiment.

Cross-namespace modification
  Attack: a department modifies another department's names.
  Mitigation: authorization uses the longest enclosing namespace; the signer
  must be that namespace's controller or a granted member. Every node applies
  the same rule to the same state.
  Test: cross-namespace experiment.

Duplicate registration / race
  Attack: two participants register the same name concurrently.
  Mitigation: the coordinator serializes operations; the state machine rejects
  the second with NAME_TAKEN. Majority commit means there is no window where
  both callers see success.
  Test: duplicate registration experiment.

Record hijack via a prohibited destination
  Attack: point a campus name at an external host for phishing or exfiltration.
  Mitigation: record policy rejects addresses outside campus space at the state
  machine level.
  Test: prohibited destination experiment.

Unauthorized revocation or transfer
  Attack: revoke or steal someone else's name.
  Mitigation: revocation requires owner, namespace controller or root; transfer
  requires the owner to initiate and the recipient to accept, with records frozen
  in between.
  Test: ownership transfer experiment, state tests.

Reaching a single node to bypass policy
  Attack: send a write directly to a follower.
  Mitigation: followers forward to the coordinator and never apply uncommitted
  entries. Policy is evaluated by the state machine on every node.
  Test: cluster smoke phase 2.

Node failure
  Attack/fault: crash a node or partition it.
  Mitigation: majority commit; continued writes with one of three down; refusal
  without a majority; append-only catch-up on rejoin.
  Test: cluster smoke phases 3-6.

Acknowledged write not yet publishable
  Fault: the API acknowledges after majority storage while followers have not
  applied the entry, so a DNS majority still serves the old revision.
  Mitigation: publication barrier B; optional read-side detector C.
  Residual: B adds latency and can time out ambiguously after commit; C may
  return SERVFAIL. Neither is Byzantine-safe.
  Test: commit-lag A/B/C harness; test_commit_hold.py.

Silent history editing
  Attack: alter or delete an audit record on one node.
  Mitigation: hash chain; verification reports the first broken record. Nodes
  that diverge are detectable by comparing revisions and chain heads.
  Residual: a malicious majority could rewrite the whole chain; there is no
  external timestamp/anchor.
  Test: audit chain tampering test.

Stale DNS data after revocation
  Fault: a revoked name keeps resolving.
  Mitigation: DNS snapshots include only non-revoked domains in active
  namespaces. Withdrawal is observed after commit plus the refresh time.
  Residual: resolver caches may serve the old answer until the 30-second TTL.
  This is inherent to DNS, not a defect, and is measured.
  Test: revocation experiment.

Lying DNS node
  Attack: one node returns a forged A record.
  Mitigation: the quorum resolver compares all three answers and requires two to
  agree. One liar is outvoted.
  Residual: two colluding nodes can lie; DNSSEC is not implemented. A single node
  can also claim a fake high revision and force fail-closed behaviour under the
  responses watermark; signed tokens identify the claimant but do not make the
  claim true.
  Test: quorum_dns experiment.

15.4 Trust boundaries
---------------------
  untrusted                     trust boundary                  trusted
  ---------                     --------------                  -------
  any client  --signed op-->  [ verify signature ]  -->  state machine
  any client  --signed op-->  [ namespace policy ]  -->  state machine
  follower    --append RPC->  [ term / log rules ]  -->  replicated log
  DNS client  --query------>  [ 2-of-3 agreement + freshness ]  -->  answer or SERVFAIL

The registry never trusts the transport. A node that receives an operation
verifies it itself; it does not rely on the forwarding node having done so.

15.5 Residual risk register
---------------------------
Root key compromise          Critical  Accepted; 2-of-3 root signatures specified,
                                       not built.
Unauthenticated internal RPC High      /internal/* is loopback-only in the demo;
                                       production needs mutual TLS.
Owner key loss               High      No recovery; break-glass policy specified,
                                       not built.
Byzantine registry node      High      Out of scope; explicitly not claimed.
Two colluding DNS nodes      High      Majority trust boundary; DNSSEC not built.
Portal holds private keys    High      Demo-only; documented in the UI.
Nonce table grows            Low       Acceptable at prototype scale.
Log never compacted          Low       Acceptable at prototype scale.
.test only                   Low       Deliberate isolation.
DNS cache holds revoked TTL  Low       Measured, inherent to DNS.
No external audit anchor     Medium    Hash chain detects edits but not a full
                                       rewrite by a malicious majority.
B trusts peer revisions      Medium    Non-Byzantine self-report; not a proof.
Ambiguous write after B      Medium    Client must be idempotent; de-dup not built.

15.6 What we deliberately do not claim
--------------------------------------
- That the system eliminates central authority. The root authority remains.
- That it resists a malicious registry node in consensus.
- That two colluding DNS nodes cannot lie.
- That B or C is Byzantine fault tolerance.
- That B is currently the default. It is opt-in.
- That RAM-DNS is novel or generally superior to B. Its novelty and incremental
  benefit are not established.
- That it is a production PKI. Key enrolment and recovery are specified, not
  implemented.
- That every client on the internet can resolve these names. Only clients pointed
  at the lab resolver can.
- That DNS answers are cryptographically signed in the DNSSEC sense. DNSSEC is
  future work.

16. AUDIT AND HISTORY
================================================================================

16.1 Two views
--------------
- history: a per-target list of operations (used on the domain detail page).
- audit: a global, hash-chained list of every accepted operation.

16.2 The audit record
---------------------
  {
    "seq": 12,
    "revision": 12,
    "op": "update_records",
    "target": "techfest.cs.test",
    "actor": "<public key>",
    "detail": { "before": {...}, "after": {...} },
    "prev_hash": "<hash of record 11>",
    "hash": "sha256(canonical_json(record without hash))"
  }

16.3 Verification
-----------------
verify_audit_chain() recomputes every hash and checks every prev_hash. It returns
ok, length, head, or the first broken record. Changing any historical record
invalidates every hash after it. The Audit page shows the verification badge.

16.4 What the chain does and does not prove
------------------------------------------
It proves that a record was not edited in isolation without breaking the chain.
It does not prove that a malicious majority did not rewrite the entire chain. For
that you need an external anchor (a timestamp, a published head, or a separate
witness). This is a documented limitation.

16.5 Why history matters for the demo
-------------------------------------
When you update a record, the domain page shows before/after. When you transfer
or revoke, the history shows who did it and at which revision. This is what makes
the registry auditable rather than just a key-value store.

17.3 How the portal signs
-------------------------
The portal loads the demo key files and signs on behalf of the selected identity.
The identity picker sets a cookie. This is a demo convenience. In production the
private key never leaves the user's device.

17.4 Live updates
-----------------
app.js polls /partials/status every two seconds and replaces the live section,
including the event log. Submitting the query form fetches /partials/probe and
updates the result table without a full page reload. The page still works
without JavaScript; polling and partial refresh are progressive enhancement.
Forms are normal POST requests with redirects and flash messages.

17.5 Experiments page
---------------------
The page lists all experiments with title, description and expectation. Running
one calls the same ExperimentRunner used by scripts/evaluate.py. Results are kept
in memory for the session; restarting the portal clears them. The CLI writes the
markdown report.

17.6 Why server-rendered?
-------------------------
The demo must work offline and on any machine. No bundler, no npm, no CDN. A
registry administration tool benefits from explicit form submissions and clear
confirmation, not optimistic UI.

18.7 Three-minute console path
------------------------------
1. Baseline (25 s)
   Open http://127.0.0.1:8000 and query techfest.cs.test. Point out the three
   registry nodes, one coordinator, the per-node DNS responders, and the quorum
   resolver. The n1/n2/n3 rows are direct UDP queries; the resolver row is a
   separate decision with its own vote map. Revisions come from the EDNS token
   and /status.

2. One node lies (30 s)
   Click "Make n3 lie". n3 returns 10.20.5.66; n1 and n2 return the honest
   address; the resolver returns the honest majority answer. FAULT ACTIVE names
   the forged record.

3. Lose DNS quorum (30 s)
   Click "Pause n2 + n3". n1 still answers; n2 and n3 time out; the resolver
   returns SERVFAIL. The registry APIs stay up and the audit chain is unchanged.

4. Registry quorum still commits (30 s)
   While DNS is paused, register or update a name as Alice. The write commits;
   every registry node applies it, so the revision counters advance even on the
   paused nodes. The resolver still returns SERVFAIL because only n1 answers.
   Reset the pause to let the resolver see a majority again.

5. Stale majority (40 s)
   Click "Freeze n1 + n2 DNS", then update techfest.cs.test. n1 and n2 keep
   serving their real frozen snapshot at the old revision; n3 serves the new
   commit. The semantic majority is stale. The resolver reports STALE_MAJORITY,
   retries, and returns SERVFAIL instead of the old address. Click "Thaw DNS
   snapshots" to restore the new answer.

6. Recover (25 s)
   Click "Reset DNS faults". All three nodes answer the current committed value,
   the resolver returns a majority answer, and the banner clears. This is a flag
   clear, not a restart or a log rollback.

7. Authority and audit (20 s)
   Switch to Mallory and try to update Alice's name: UNAUTHORIZED, record
   unchanged. Open Audit and show that the hash chain still verifies.

18.8 Manual DNS fault demo

The console buttons are the normal path. The same controls can be driven

18.10 Failure demo
------------------
For a clean scripted failure demo, stop the live demo and run:

  python scripts/cluster_smoke.py

It starts its own three nodes on 9101-9103 with data/smoke and runs the nine

19.7 Why the failure tests matter more than the happy path
----------------------------------------------------------
A registry that works when everyone is honest demonstrates nothing. The evidence
that carries weight is:

  - the same forged operation is rejected whether sent to the coordinator or a
    follower,
  - a write is refused when a majority is unavailable,
  - a node that missed entries converges to exactly the committed revision,
  - one lying DNS node cannot change the majority answer,
  - a semantically agreeing but stale majority is refused instead of served as
    current,
  - a barrier-acknowledged write is not followed by a stale majority,
  - a barrier timeout is reported as ambiguous rather than as a definite failure.

19.8 Threats to validity
------------------------
- Single host: no true network partition. Process termination and synthetic
  commit holds are used instead.
- Three nodes only: cannot distinguish 2-of-3 from larger quorums; the code
  computes quorum from configuration, not hard-coded.
- Small sample: 12 comparison trials per variant plus 20 natural trials; p99
  values from 3-12 samples are indicative, not stable.
- Demo keys on disk: portal signing is not realistic.
- Experiments mutate state: unique suffixes keep results stable.
- Timing on a laptop: latency varies with load; report observations, not
  benchmarks.
- No Byzantine registry consensus: a malicious node is out of scope.
- No DNSSEC: DNS answers are not cryptographically signed in the DNSSEC sense.
- B does not cover responder freeze: it checks registry dns_revision, not the
  responder's serving_revision.
- C's watermark is incomplete: if every responder is stale, C cannot know a newer
  commit exists.
- The baseline 100% rate is harness-specific: production prevalence is unknown.


================================================================================
20. LIMITATIONS AND HONEST CLAIMS
================================================================================

This section is your defence against overclaiming. Say these before someone else
does.

20.1 Centralization that remains
--------------------------------
- Root trust anchor: the root key authorizes top-level namespaces.
- Static membership: the three node URLs are configured, not discovered.
- .test only: the prototype is not delegated from the real DNS root.
- Portal key custody: the demo server holds private keys.
- Quorum threshold: 2 of 3 is a configuration choice, not a universal law.
- No DNSSEC: DNS answers rely on majority trust, not cryptographic proofs.

20.2 Technical limitations
--------------------------
- No Byzantine-fault-tolerant consensus. A malicious node can violate the
  replication protocol. The DNS majority can outvote one liar, but that is not
  BFT consensus.
- Two colluding DNS nodes can lie. Majority trust is the boundary.
- B is opt-in, not the default. The unsafe baseline remains available for
  comparison.
- B adds a replication round trip and can time out ambiguously after commit.
  Idempotency/de-duplication is a next step, not implemented.
- B checks registry dns_revision, not the responder's serving_revision. A frozen
  responder can still let B acknowledge.
- C can return SERVFAIL during a transient stale window; its local lookup p50 is
  about 118 ms versus 11 ms for the semantic-only baseline.
- C's watermark cannot see a commit no responder has seen.
- No real network partition testing. Process death and synthetic holds are not
  the same as a split network.
- No dynamic membership. Adding a node requires config changes.
- No log compaction or snapshots. The log grows without bound.
- No key recovery. A lost owner key means a lost domain.
- Only IPv4 A records. No AAAA, TXT, CNAME, MX, SRV, DNSSEC or zone transfers.
- No recursion. The quorum resolver is a forwarder, not a general recursive
  resolver.
- No rate limiting or DoS protection.
- No privacy layer. Registry state and audit are public inside the lab.
- No production key management. No HSM, no client-side signing, no enrolment.
- RAM-DNS novelty and incremental benefit over B are not established.

20.3 The one-paragraph honest summary
-------------------------------------
DCDNS is a permissioned prototype. It decentralizes namespace administration,
state replication, DNS serving and the DNS answer decision. It does not
decentralize the root trust anchor, node membership or key custody. It tolerates
crash faults and one lying DNS node, not Byzantine consensus or two colluding
nodes. It is authoritative for .test only, supports A records only, and has no
DNSSEC. The project's central result is a real acknowledged-write stale-majority
failure and a standard write-path fix, B, with an optional read-side detector, C.
Those boundaries are deliberate and documented, because a prototype that claims
more than it demonstrates is worse than one that is precise.

20.4 What would production require?
-----------------------------------
- Make B the default and add an end-to-end majority-visibility regression test.
- Add idempotency keys / operation de-duplication for ambiguous timeouts.
- Close B's responder gap by reporting serving_revision, or keep C in front.
- Replace the custom log with etcd/Raft or a proven BFT protocol if malicious
  nodes are in scope.
- Mutual TLS between nodes; internal APIs not on loopback only.
- Client-side signing with hardware-backed keys; no private keys on the portal.
- Dynamic membership and log compaction/snapshots.
- DNSSEC or signed zone snapshots.
- Integration with the university's real delegated zone and DNS/DHCP.
- Monitoring, rate limiting, backups, disaster recovery.
- External audit anchoring or a witness for the hash chain.
- Multi-site deployment and real partition testing.
- A professional prior-art search before any patent filing or novelty claim.


================================================================================
21. PRESENTATION Q&A: TYPICAL QUESTIONS AND STRONG ANSWERS
================================================================================

Use these as speaking notes, not as a script to read word for word. The best
answers are short, then one supporting detail, then an honest limitation.

Q1. What is DCDNS in one sentence?
A: "It is a permissioned campus DNS registry where departments own their part of
   the namespace, three nodes replicate the state, every node serves DNS, and a
   client resolver accepts an answer only when a majority agrees."

Q2. What problem does it solve?
A: "It lets a university delegate DNS administration without giving up a coherent
   namespace or an audit trail. Departments can manage their own names, but every
   change is signed, authorized, replicated and revocable."

Q3. What is the main result?
A: "We found and reproduced a gap between 'committed' and 'publishable to DNS'.
   The baseline acknowledged a write after a majority stored it, while followers
   applied it later, so a DNS majority could still serve the old address. We
   measured 12 of 12 acknowledged writes stale, then fixed it with a publication
   barrier B. RAM-DNS C is an optional read-side detector."

Q4. Why not just use a database and a DNS server?
A: "A database solves storage, not authority. The hard part is who may delegate a
   namespace, who owns a name, how a transfer works, how a revocation is proven,
   and how every node reaches the same verdict. That logic is the state machine.
   And a single database plus a single DNS server is still two central points of
   failure. We replicate the registry and serve DNS from every node."

Q5. Is this a blockchain?
A: "No. There are no blocks, mining, tokens or proof-of-work. It is a permissioned
   registry with a replicated log and a known set of nodes. A blockchain is
   designed for trustless open membership; this is designed for a university that
   already knows its departments."

Q6. Is it truly decentralized?
A: "It is decentralized in four specific ways: namespace authority is delegated,
   state is replicated across independent nodes, every node serves DNS, and the
   client answer is decided by majority agreement plus a revision freshness check.
   It is not decentralized in membership discovery, root trust, or key custody. We
   are precise about that."

Q7. What is still centralized?
A: "The root trust anchor, the static node membership, the .test lab zone, the
   demo key files, and the quorum threshold. Those are deliberate prototype
   choices, documented in the README and threat model."

Q8. Why three nodes?
A: "Three is the smallest useful majority. One node down: 2 of 3 still commit and
   still answer DNS. Two down: no majority, so writes stop and DNS returns
   SERVFAIL. One liar: the other two outvote it. Two liars: they can outvote the
   honest node, which is the documented boundary."

Q9. What is a quorum?
A: "A majority: floor(N/2) + 1. For three nodes, two. The registry needs a quorum
   to commit a write. The DNS resolver needs a quorum of agreeing answers. Same
   number, different planes."

Q10. Why is there a leader? Isn't that centralization?
A: "The leader is a temporary write coordinator, not a central authority. It is
   elected as the lowest-id node among the reachable majority, it has no extra
   signing key, it cannot change a record without a valid signature, and it can be
   killed and replaced. A single writer is needed to order unique-name and
   ownership operations. The cluster is a full mesh; the leader is a role, not a
   hub. In the presentation I usually call it the coordinator."

Q11. What happens if the leader dies?
A: "The remaining two nodes see a majority and elect the lowest-id of the two.
   A new term starts, the new coordinator catches up on the log, and writes
   continue. The smoke test kills the leader and proves this. DNS is unaffected
   because every node already answers independently."

Q12. What happens if one node lies?
A: "For DNS, the other two outvote it; the resolver returns the honest majority
   answer. For registry consensus, a lying node is out of scope: this is not
   Byzantine-fault-tolerant consensus. We demonstrate the DNS case with the chaos
   endpoint: n3 returns 10.20.5.66, the resolver returns the honest address."

Q13. What if two nodes lie?
A: "Then they are the majority and the resolver accepts their semantic answer.
   RAM-DNS does not fix that: if the colluding majority also claims a current
   revision, it is indistinguishable from an honest current majority. That is the
   honest boundary of majority trust. DNSSEC or signed zone snapshots would be
   needed for cryptographic proof, and we have not implemented that."

Q14. What if two nodes are down?
A: "The remaining node is isolated: it cannot commit writes and returns NO_QUORUM.
   The DNS resolver requires 2 of 3 configured nodes, so it returns SERVFAIL even
   if the single node answers. This is deliberate: we prefer no answer to trusting
   one node."

Q15. How does the DNS resolver choose an answer?
A: "It sends the same query to all three node responders, reduces each response to
   its semantic content (RCODE plus answer records), groups identical answers, and
   returns one only if at least two nodes are in the same group. It ignores
   transaction IDs, harmless flags, TTL differences and record order. It then reads
   the serving revision from each answer's EDNS token, computes the committed
   revision watermark, and applies the F1 freshness condition to the winning
   majority. A stale majority is retried a bounded number of times, then refused
   with SERVFAIL (or marked stale if that policy is selected)."

Q16. Is the resolver a single point of failure?
A: "It is a single process in the demo, but not a single point of authority. It
   has no zone and cannot invent an answer. It may hold node public keys to verify
   revision tokens, but those keys do not let it change the answer. Clients can
   query any node directly, and you can run multiple resolvers. If it dies, clients
   pointed at it fail, but no registry data is lost. In production the resolver
   function would be replicated or built into clients."

Q17. How do you stop someone registering someone else's name?
A: "The signer must be authorized in the governing namespace: the controller, the
   root, or a member with can_register. Mallory has a valid key but no authority,
   so her registration is rejected with UNAUTHORIZED. The check runs on every
   node, not just the entry point."

Q18. How do you stop replay?
A: "Each operation has a random nonce. The state machine records actor|nonce when
   it accepts an operation. A byte-for-byte resubmission is rejected with
   REPLAY_DETECTED even though the signature is still valid."

Q19. How are private keys handled?
A: "In the demo, the portal loads key files from identities/ and signs on the
   selected identity's behalf. That is a convenience and a limitation. In
   production, signing happens on the client with a hardware-backed key and the
   server never sees the private key."

Q20. What happens when a domain is revoked?
A: "The domain becomes REVOKED, the DNS snapshot excludes it, and queries return
   NXDOMAIN after the commit propagates. The history and audit remain. The name
   cannot be re-registered, which prevents a revoked project name from being
   quietly taken over."

Q21. What happens during an ownership transfer?
A: "The owner initiates; the domain becomes PENDING_TRANSFER and records are
   frozen. The proposed new owner must accept. Until then the name keeps resolving
   from the frozen record, so a handover does not cause downtime. The old owner
   can cancel before acceptance. After acceptance, the new owner controls it."

Q22. Why .test?
A: ".test is reserved by RFC 6761 for testing and will never collide with a real
   public name. .local was rejected because it triggers multicast DNS behaviour;
   .campus is not a delegated TLD. A real deployment would use a subdomain of the
   university's owned zone."

Q23. Why not use CoreDNS or BIND?
A: "They are good at serving a zone; they do not implement delegated registry
   authority, signed operations, ownership transfer, revocation and audit. We
   built the registry rules and a small DNS wire engine. In production, the
   registry could render a zone file or push RFC 2136 updates into BIND/CoreDNS."

Q24. Why not use etcd or Raft?
A: "etcd was considered and remains the production path. For this prototype I
   wanted zero external dependencies and the workload allows a simpler protocol:
   one writer at a time, followers never originate entries, so logs are prefixes
   and no truncation is needed. The trade-off is no Byzantine tolerance and a less
   battle-tested implementation, which I state explicitly."

Q25. Why not use a blockchain?
A: "A permissioned campus registry does not need mining or open membership. A
   blockchain would add latency, complexity and a token/consensus model that does
   not match the governance problem. We need known institutions, fast commits and
   clear authority, not trustless open participation."

Q26. Why not DNSSEC?
A: "DNSSEC signs DNS answers; our Ed25519 signatures sign registry operations.
   They solve different problems. DNSSEC is future work. The DNS layer uses
   majority agreement plus a signed revision token that proves which node made a
   freshness claim. The token is not a DNSSEC signature and does not give
   cryptographic proof of the answer to an ordinary resolver."

Q27. How do you know it works?
A: "Four layers of evidence: 108 unit and wire tests, 9 cluster failure/recovery
   checks with real processes, 14 portal flow checks, and 12 live security
   experiments, including the stale-majority experiment. The A/B/C harness adds
   the controlled comparison: 12 of 12 baseline writes stale, 3 of 3 barrier
   controls clean, 9 of 9 held barrier writes ambiguous and later convergent. The
   experiments are the same code the portal buttons call, so the report cannot
   drift from the demo."

Q28. What are the biggest limitations?
A: "No Byzantine registry consensus; two colluding DNS nodes can lie; B is opt-in
   and trusts self-reported peer revisions; B can time out ambiguously after
   commit, so idempotency is still needed; B does not cover a frozen responder; a
   single node can raise the response watermark with a fake high revision and
   force fail-closed behaviour; the watermark can only reflect commits some
   responder has seen; static membership; no real network partition testing; no key
   recovery; only IPv4 A records; no DNSSEC; demo keys on the portal. All are
   documented."

Q29. What would production need?
A: "Make B the default with a majority-visibility regression test, add
   idempotency/de-duplication, close B's responder gap or keep C in front, use
   proven consensus (Raft/etcd or BFT if malicious nodes are in scope), mutual TLS
   between nodes, client-side key custody, dynamic membership, log compaction,
   DNSSEC or signed zones, integration with the real university zone, monitoring,
   rate limiting, backups and multi-site testing."

Q30. Can it scale?
A: "The prototype is three processes on one host; it is not a scalability study.
   The protocol is O(nodes) per write and the DNS resolver queries all nodes, so
   it is intended for a small permissioned set, not thousands of nodes. A
   production design would shard namespaces or use a proven consensus cluster."

Q31. What about latency?
A: "The registry heartbeat is 0.25 s. Baseline writes acknowledged at a p50 of
   about 7.9 ms in the comparison; barrier writes at about 14.8 ms because of the
   extra apply round trip. Semantic lookups were about 11 ms; RAM-DNS lookups about
   118 ms because of retries and fail-closed behaviour. These are observations,
   not benchmarks."

Q32. What about caching?
A: "DNS answers carry a 30-second TTL. A resolver cache can serve a revoked or
   updated record until the TTL expires. That is inherent to DNS. The evaluation
   measures the authoritative/quorum answer, not every cache in the world."

Q33. What about internal API security?
A: "The internal endpoints are bound to loopback in the demo and are not meant to
   be exposed. Production requires mutual TLS and network policy between nodes.
   The chaos and commit-hold endpoints are disabled unless --chaos is set and are
   loopback-only."

Q34. Can the root forge my record?
A: "The root cannot forge an owner's signature. It can revoke a domain or
   namespace and can register names, but any root action is a root-signed
   operation in the audit log. It cannot silently rewrite your record as if you
   signed it."

Q35. What if the root key is compromised?
A: "Delegation is compromised: the attacker can delegate namespaces and revoke
   things. It cannot forge an owner's signature, so record-level forgery would
   still appear as a root-signed audit entry. Mitigation is 2-of-3 root signatures
   and offline storage; specified, not implemented."

Q36. What if the audit log is tampered with?
A: "The hash chain detects any edit that breaks the chain, and verification reports
   the first broken record. A malicious majority could rewrite the whole chain;
   there is no external anchor. That is a residual risk, stated honestly."

Q37. Can a revoked name be re-registered?
A: "No. The name stays in the domains table as a tombstone, so a new registration
   returns NAME_TAKEN. This prevents takeover of a revoked name. The same applies
   to a revoked namespace."

Q38. Can a domain move between namespaces?
A: "No. A domain is registered inside its governing namespace and there is no move
   operation. You would revoke and register under the new namespace, which is a
   deliberate, auditable action."

Q39. What about privacy?
A: "Registry state and audit are public inside the lab: names, owners (public
   keys), records and history. There is no privacy layer, no GDPR work, and no
   attempt to hide who owns what. A production deployment would need a data
   protection review."

Q40. What is the novel or interesting part?
A: "The main result is the acknowledgement/publication gap and the barrier that
   closes it. The engineering package combines delegated namespace authority,
   signed operations, quorum replication, per-node DNS serving, client-side
   majority agreement, and an optional revision-aware freshness detector. We do
   not claim that RAM-DNS is novel; the academic review found no demonstrated
   novelty, and the barrier itself is standard commit/apply discipline."

Q41. What did you learn?
A: "That the hard part of a registry is authority and failure semantics, not
   storage. And that 'decentralized DNS' is not one thing: serving, data,
   authority and answer agreement can be decentralized separately. A majority can
   agree on stale data, and an acknowledgement is only as strong as the state it
   promises."

Q42. What was the hardest part?
A: "Keeping the state machine deterministic while adding replication, and making
   the DNS layer honest: avoiding a central publisher, comparing semantic answers
   rather than packets, and handling no-majority with SERVFAIL instead of silently
   trusting one node. The subtle part was proving the commit/apply window and
   closing it without hiding the ambiguous-timeout case."

Q43. Why Python?
A: "Rapid, readable prototyping with excellent cryptography and HTTP libraries.
   Performance is not the goal; correctness and demonstrability are. A production
   hot path could be rewritten or delegated to proven infrastructure."

Q44. What is the one thing you want the audience to remember?
A: "A write acknowledgement must match what the DNS layer can actually serve.
   B is the fix; C is the detector. Authority is delegated, state is replicated,
   and every node serves DNS."

Q45. If I only remember one diagram, what is it?
A: "Three registry nodes in a mesh, each with its own DNS port. A client resolver
   fans out to all three and returns an answer only when two agree. The registry
   log is majority-committed; the DNS answer is majority-agreed; and the barrier
   makes sure a success is not acknowledged before a majority can publish it."


================================================================================
22. ELEVATOR PITCHES
================================================================================

22.1 Thirty-second pitch
-----------------------
"DCDNS is a permissioned campus DNS registry. The root delegates namespaces to
departments; every change is signed with Ed25519 and committed by a majority of
three nodes. Each node also serves DNS from its own committed state. We found that
the original API acknowledged a write before a majority could serve it, so a DNS
majority could return the old address. We implemented a publication barrier,
currently opt-in, and added an optional revision-aware detector. It is a working
prototype with a portal, 108 tests, 9 cluster checks and 12 live experiments."

22.2 Two-minute pitch
--------------------
"Universities have one DNS namespace but many departments. Central IT does not
want to create every name, but it also cannot let anyone claim any name. DCDNS
solves that with delegated namespace authority. The root authorizes cs.test and
library.test; the CS controller can then delegate team.cs.test to a student and
grant members permission to register names. Every operation is signed with
Ed25519, so ownership is cryptographic, not a password in a database.

The registry is replicated across three nodes. A write is committed when a
majority stores it. If one node dies, the other two continue; if the coordinator
dies, another takes over; if two die, writes stop rather than diverge.

The interesting part is the boundary between the registry and DNS. Every registry
node is also an authoritative DNS server, on its own port. There is no separate
DNS publisher. A client-facing resolver sends each query to all three nodes and
returns an answer only when two agree. We discovered that the original write path
acknowledged after a majority stored the entry, while followers applied it only on
the next replication push. For a short window, two of three DNS responders still
served the old address, so the semantic majority was stale. We reproduced that in
12 of 12 acknowledged writes, and 20 of 20 in a natural run.

The primary fix is a publication barrier, currently opt-in: a write succeeds only
after a majority reports applying the revision to its DNS state. If they cannot,
the write fails closed with an ambiguous timeout instead of falsely succeeding.
We also implemented a read-side detector, RAM-DNS, which attaches a signed
serving revision to each DNS answer and rejects a stale majority. It is useful
defence in depth, especially for a frozen responder, but it does not repair the
write path and it costs availability.

The honest boundaries: the root trust anchor remains, membership is configured,
the registry consensus is not Byzantine-fault-tolerant, two colluding DNS nodes
can lie, the watermark can only reflect commits some responder has seen, and
DNSSEC is not implemented. The evidence is 108 tests, 9 cluster failure checks,
14 portal flow checks and 12 live experiments, plus the controlled A/B/C harness."

22.3 Technical two-minute pitch
-------------------------------
"The system has two planes. The registry plane is a deterministic state machine
over signed operations: delegate_namespace, grant_member, register_domain,
update_records, transfer_initiate/accept/cancel, revoke_domain, revoke_namespace
and rotate_controller. The envelope has a version, actor, nonce, timestamp, body
and Ed25519 signature over canonical JSON with domain separation. The state
machine validates the envelope, signature, nonce, authorization and record policy
on a clone before the coordinator appends anything. A write is committed when a
majority stores it; the state applies committed entries and refreshes a flat DNS
snapshot.

The subtle bug is that commit and apply are distinct. The coordinator snapshots
the commit index before replication, so the first push for entry i advertises
i-1. Followers store i but do not apply it. The coordinator advances commit,
applies locally, and the baseline acknowledges. An immediate DNS query sees one
node at revision i and two at i-1. The semantic resolver's 2-of-3 rule returns the
old address. The publication barrier adds an applied-majority check: the
coordinator counts itself only after refreshing its DNS snapshot, and counts a
follower only when the append response reports dns_revision >= i. It pushes the
new commit index and re-checks before acknowledging. A timeout after commit is
reported as ambiguous.

The DNS plane is per-node. Each node runs a UDP responder on its own port and
answers from its committed snapshot with a 30-second TTL, attaching its serving
revision, a zone digest and an optional Ed25519 signature in EDNS option 65001.
The client resolver queries all configured nodes, reduces responses to RCODE plus
sorted answer records, and requires 2 of 3 agreement. It ignores transaction IDs,
flags, TTLs and record order. It can then apply F1/F2/F3 freshness over the
winning majority relative to the watermark; a stale majority is retried and then
refused with SERVFAIL. No majority means SERVFAIL.

The trade-offs are explicit: single-writer coordinator for ordering, no BFT, no
dynamic membership, no log compaction, no DNSSEC, no AAAA, and B still opt-in.
The evidence includes wire-level tests, majority and freshness tests, a real
three-process cluster smoke test with leader failover and catch-up, a chaos
experiment where one node lies and is outvoted, a stale-majority experiment with
real frozen snapshots, and an A/B/C harness with raw trial records."

23. TROUBLESHOOTING
================================================================================

Port already in use
  Stop the python processes whose command line mentions dcdns.node,
  dcdns.portal, dcdns.quorum_resolver or run_demo, then rerun.

Portal shows no quorum
  Wait a few seconds; the coordinator election is asynchronous. If it persists,
  check the node logs in data/live/logs/n1.log, n2.log, n3.log. Rerun with
  --fresh if the data is inconsistent.

DNS returns nothing
  Check:
    - the demo was started without --no-dns,
    - the node logs show the DNS responder bound its port,
    - http://127.0.0.1:5380/metrics is reachable,
    - you are querying the right port with python -m dcdns.dig.
  On Windows, nslookup ignores -port; use dig.py.

Quorum experiment fails with chaos disabled
  The quorum_dns experiment needs nodes started with --chaos. run_demo enables it
  unless you pass --no-dns. Start nodes manually with --chaos if needed.

cluster_smoke.py fails with address in use
  Stop the live demo first. The smoke test uses 9101-9103 and data/smoke.

Stale data after a change
  The dashboard shows per-node revisions; wait for convergence. If a node is
  isolated, it will not catch up until it can reach a majority. Use --fresh for a
  clean demo. To test the fixed path, run the nodes with --publication-barrier
  and query a majority of DNS responders immediately after the write.

Barrier writes time out
  If the followers cannot apply the committed entry before the 2.5 s deadline,
  NO_QUORUM with ambiguous: true is expected. The write may still commit later.
  Check that the followers are reachable and not held by a chaos experiment.

RAM-DNS returns SERVFAIL after an update
  Check the resolver decision: a stale majority, missing/invalid revision token,
  or no majority can all produce SERVFAIL. Wait for convergence or thaw frozen
  responders, then query again. If this is unacceptable, the deployment should
  fix the write path with B rather than rely on C.

Portal 500 after editing a template
  Check data/live/logs/portal.log. Jinja errors show the template and line. The
  portal auto-reloads templates, but a syntax error will break the page.

A revoked name still resolves
  A resolver cache may hold it until the 30-second TTL. Query the quorum resolver
  directly. If the authoritative answer is still present, check that the
  revocation committed and the node revision advanced.

Two nodes down and DNS returns SERVFAIL
  This is expected. The resolver requires 2 of 3 configured nodes. It will not
  trust a single node.

Everything is slow
  The demo runs three nodes, a resolver and a portal on one machine. Check CPU
  load and antivirus scanning of the data directory. Timing numbers are
  observations, not benchmarks.
